Objet et périmètre

Le Serveur MCP expose des bases de données de l’entreprise à des assistants d’intelligence artificielle via le Model Context Protocol (MCP), standard ouvert qui permet à un assistant d’appeler des « outils » distants. Il comprend :

  • un serveur MCP distant (transport Streamable HTTP), avec une URL par connexion de base de données ;
  • un serveur d’autorisation OAuth 2.1 : chaque assistant agit avec le compte de son utilisateur ;
  • une interface web d’administration : connexions, utilisateurs, rôles, attribution des accès.
ÉlémentPrise en charge
Bases relationnellesMySQL 5.7+ / MariaDB, Microsoft SQL Server (2012+, Azure SQL), PostgreSQL
Bases non relationnellesMongoDB (si l’extension PHP mongodb est installée), Redis
Clients MCP testésMicrosoft 365 Copilot et Teams (via un agent Copilot Studio), Claude (claude.ai, Desktop, Claude Code), ChatGPT (mode développeur), Cursor ; tout client MCP gérant OAuth (ou via mcp-remote)
HébergementWindows Server + IIS (PHP en FastCGI), base MySQL pour les données de l’application

Serveur MCP et outils

Point d’accès

  • URL : https://luxewtey.com/mcpsolid/mcp/{connection}, où {connection} est l’identifiant aléatoire (16 caractères) de la connexion.
  • Transport : Streamable HTTP sans état ; chaque message JSON-RPC est une requête POST. GET et DELETE renvoient 405 (pas de flux SSE serveur ni de session).
  • Chaîne de traitement : auth:api (jeton Passport) → AuthorizeMcpConnection → DatabaseServer → outil.

Traitement d’une requête

  1. auth:api — vérifie le jeton d’accès (signature RSA, expiration, révocation). Sans jeton valide : 401 avec l’en-tête WWW-Authenticate et resource_metadata, qui déclenche la découverte OAuth côté client.
  2. AuthorizeMcpConnection — charge la connexion (404 si inconnue), vérifie que le titulaire du jeton est actif et y a accès (403 sinon), que la connexion n’a pas expiré (403), puis met à jour last_used_at (au plus une fois par minute).
  3. DatabaseServer::boot — fixe le nom du serveur et des instructions destinées au modèle : type de base, mode lecture seule, limite de lignes, consigne d’explorer la structure avant d’écrire des requêtes.
  4. Outil — n’est exposé que s’il correspond au type de base et au mode (DatabaseTool::shouldRegister) ; ouvre la base, exécute, sérialise en JSON. Les annotations MCP (readOnlyHint, destructiveHint) sont renseignées.

Authentification et autorisation

Parcours de connexion d’un utilisateur

Un utilisateur s’authentifie deux fois, avec le même compte : sur l’interface web (session), puis, pour chaque assistant, par une autorisation OAuth. Le parcours complet :

#ÉtapeMécanisme
1Invitation (administrateur)POST /users crée le compte (status = invited, sans mot de passe) et envoie par e-mail le lien https://luxewtey.com/mcpsolid/invitation/{jeton} (usage unique, 7 jours). L’administrateur attribue les connexions (PUT /connections/{id}/users).
2Création du mot de passeGET/POST /invitation/{jeton} : mot de passe (10 caractères minimum, bcrypt), status = active, jeton supprimé, session ouverte.
3Connexion à l’interfacehttps://luxewtey.com/mcpsolid/login : e-mail + mot de passe, session Laravel ; tentatives limitées (voir ci-dessous).
4Lien MCPPage Mes connexions : pour chaque connexion attribuée, l’URL https://luxewtey.com/mcpsolid/mcp/{id} à copier.
5Branchement de l’assistantL’assistant appelle l’URL MCP, reçoit 401, découvre le serveur OAuth, s’enregistre, puis ouvre /oauth/authorize : l’utilisateur se connecte (session de l’étape 3) et clique sur Autoriser. L’assistant reçoit un jeton lié à ce compte (détails en 4.3).

Pour Microsoft Copilot, l’étape 5 est réalisée une fois par l’administrateur dans Copilot Studio (agent publié, voir 4.5), puis chaque collaborateur autorise son propre compte à la première utilisation de l’agent.

Interface web

  • Session Laravel (pilote database), cookie Secure en HTTPS, protection CSRF sur tous les formulaires.
  • Mots de passe hachés en bcrypt (12 tours), 10 caractères minimum.
  • Limitation des tentatives : 10 échecs par couple IP + e-mail, et 100 échecs au total, sur 15 minutes. Une empreinte factice est vérifiée pour les comptes inconnus, afin que le temps de réponse ne révèle pas l’existence d’un compte.
  • Invitations : jeton aléatoire de 48 caractères, dont seule l’empreinte SHA-256 est stockée ; usage unique ; 7 jours ; un nouveau lien invalide le précédent. Envoi par e-mail SMTP (InvitationMail) ; en mode MAIL_MAILER=log, rien n’est envoyé (pour ne pas écrire le lien dans les journaux) et le lien est affiché à l’administrateur.
  • Aucune inscription libre : les comptes sont créés par un administrateur, ou par la commande php artisan mcp:admin.

Déroulement d’une première connexion

  1. Assistant — POST /mcp/{id} sans jeton → 401 + WWW-Authenticate: Bearer resource_metadata=…
  2. Assistant — lit les métadonnées (RFC 9728 puis RFC 8414), s’enregistre via /oauth/register.
  3. Navigateur — ouvre /oauth/authorize (avec code_challenge et resource) ; l’utilisateur se connecte si nécessaire, puis voit l’écran de consentement (nom du client, connexion visée, compte, domaine de retour).
  4. Utilisateur — clique sur Autoriser → redirection vers l’assistant avec un code.
  5. Assistant — échange le code + code_verifier contre les jetons, puis rejoue POST /mcp/{id} avec Authorization: Bearer.

Règles d’accès

RègleImplémentation
Déclarer / gérer une connexioncanBeManagedBy : administrateurs
Utiliser une connexion (MCP)canBeUsedBy : compte actif et (administrateur ou attributaire via connection_user)
AttributionUne connexion déclarée par un administrateur n’est utilisable que par les administrateurs tant qu’elle n’est attribuée à aucun utilisateur (Gérer l’accès)
RévocationVérifiée à chaque requête MCP : retrait d’attribution, désactivation de compte ou retrait de rôle prennent effet immédiatement. La désactivation supprime aussi les sessions et révoque jetons d’accès et de rafraîchissement.

Une autorisation OAuth est accordée par utilisateur et par application (et non par connexion) : un assistant autorisé peut utiliser toutes les connexions auxquelles l’utilisateur a accès, dans la limite des URL qui lui ont été configurées.

Protection des données

Paramètres des connexions

  • Stockés dans database_connections.config avec le cast encrypted:array : chiffrement AES-256-CBC + HMAC avec APP_KEY.
  • Les mots de passe et chaînes de connexion ne sont jamais renvoyés au navigateur (publicConfig() ne transmet que des indicateurs has_password / has_connection_string). En modification, un champ vide conserve le secret existant.
  • Perte d’APP_KEY = perte des paramètres de toutes les connexions. La clé doit être sauvegardée hors du serveur et ne jamais être régénérée une fois des connexions créées.

Mode lecture seule

Une connexion en lecture seule n’expose pas les outils d’écriture, et chaque requête est en outre protégée à deux niveaux :

NiveauMécanisme
TransactionMySQL : START TRANSACTION READ ONLY ; PostgreSQL : BEGIN TRANSACTION READ ONLY ; SQL Server : transaction systématiquement annulée (ROLLBACK).
Garde-fou SQLSqlGuard : une seule instruction (hors littéraux et commentaires), qui doit commencer par SELECT, WITH, SHOW, EXPLAIN, DESCRIBE, VALUES ou TABLE ; refus des mots-clés d’écriture ou dangereux (INSERT, UPDATE, INTO, EXEC, xp_*, sp_*, OPENROWSET, LOAD_FILE, SLEEP, WAITFOR…).
PiloteMySQL : MULTI_STATEMENTS désactivé, requêtes préparées natives.
MongoDBSeuls les outils de lecture sont exposés ; $out et $merge sont refusés dans aggregate.
Redisrun_command limité à une liste blanche de commandes de lecture ; liste noire permanente (SHUTDOWN, MONITOR, ACL, MODULE, commandes bloquantes…).

Défense en profondeur.Ces protections ne remplacent pas les droits de la base. Utilisez des comptes de base en lecture seule dédiés : scripts deploy/sql/mysql-lecteur.sql et deploy/sql/sqlserver-lecteur.sql.

Autres mesures

  • APP_DEBUG=false en production : aucune trace d’erreur détaillée n’est renvoyée (les réponses MCP et OAuth sont toujours en JSON).
  • HTTPS obligatoire (URL::forceScheme('https') lorsque APP_URL est en https) ; cookies de session sécurisés.
  • TRUSTED_PROXIES à renseigner uniquement si un proxy inverse est placé devant IIS.
  • Flux de données : les résultats des requêtes sont transmis au fournisseur de l’assistant (Anthropic, OpenAI, Microsoft). Le choix des connexions exposées et des colonnes accessibles aux comptes lecteurs doit en tenir compte (données personnelles, données sensibles).

Déploiement sur IIS

Déploiement manuel par paquet .zip : ni Git, ni Composer, ni Node.js sur le serveur. Procédure détaillée : deploy/DEPLOIEMENT-IIS.md.

Prérequis du serveur

  • IIS avec la fonctionnalité CGI et le module URL Rewrite 2.1.
  • PHP 8.3/8.4 NTS x64 + Visual C++ Redistributable ; php.ini avec les extensions du chapitre 2, cgi.fix_pathinfo=0, fastcgi.impersonate=1, OPcache activé.
  • SQL Server : ODBC Driver 18 + DLL php_pdo_sqlsrv correspondant exactement à la version de PHP et à la variante NTS.
  • MySQL pour la base de l’application ; nom d’hôte public, DNS et certificat TLS ; site joignable depuis Internet.

Construction du paquet (poste de développement)

powershell -ExecutionPolicy Bypass -File deploy\package.ps1

Le script copie le projet sans les fichiers de développement (.git, tests, docs, .env, clés, journaux), exécute composer install --no-dev --optimize-autoloader --classmap-authoritative et produit dist\mcp-server-<date>-<commit>.zip (environ 10 Mo).

Première installation

  1. Créer la base et le compte MySQL : deploy\sql\mysql-application.sql (remplacer CHANGEZ-MOI).
  2. Débloquer puis extraire le .zip (ex. E:\Sites\mcp-server) ; copier .env.example en .env et le compléter.
  3. Dans une invite administrateur, à la racine de l’application : 
    php artisan key:generate --force
php artisan migrate --force
php artisan passport:keys
php artisan mcp:admin admin@domaine.com --name="Administrateur"
php artisan mcp:mail-test admin@domaine.com
php artisan config:cache
php artisan route:cache
php artisan view:cache
  4. Pool d’applications mcp-server : Aucun code managé, mode intégré, démarrage AlwaysRunning, délai d’inactivité 0.
  5. Droits : lecture/exécution sur le dossier, modification sur storage et bootstrap\cache pour IIS AppPool\mcp-server (et pour le compte qui lance les commandes Artisan).
  6. Site IIS : chemin physique = dossier public, liaison HTTPS avec SNI ; authentification anonyme = identité du pool.
  7. Vérifier depuis l’extérieur : /up, /.well-known/oauth-authorization-server, page de connexion.

Développement et tests

Poste de développement

composer install
copy .env.example .env     (APP_ENV=local, APP_DEBUG=true, APP_URL=http://127.0.0.1:8000, SESSION_SECURE_COOKIE=false, DB_*)
php artisan key:generate
php artisan migrate
php artisan passport:keys
php artisan mcp:admin vous@exemple.com
cd public
php -S 127.0.0.1:8000 ..\vendor\laravel\framework\src\Illuminate\Foundation\resources\server.php

Si l’extension sodium n’est pas activée (WAMP), préfixer les commandes par php -d extension=sodium ; désactiver Xdebug (XDEBUG_MODE=off).

Tests

  • php artisan test : 33 tests PHPUnit (garde-fou SQL, analyse des chaînes de connexion, contrôles d’accès, invitations et e-mails, protection OAuth du point MCP), sur SQLite en mémoire.
  • Validation de bout en bout réalisée avec le client OAuth du SDK MCP officiel (découverte, enregistrement, PKCE, appels d’outils, révocation) et sur les cinq moteurs de base (SQL Server, MySQL, PostgreSQL, MongoDB, Redis).

Ajouter un outil MCP

  1. Créer une classe dans app/Mcp/Tools/… héritant de DatabaseTool ; renseigner $name, $description, $types (bases concernées) et $writes (outil d’écriture).
  2. Déclarer le schéma d’entrée et implémenter handle() en passant par $this->run(fn () => …) (sérialisation, troncature, gestion d’erreurs).
  3. L’ajouter à DatabaseServer::$tools et écrire un test.
